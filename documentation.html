1. Project Overview

Ropo is an interactive bilingual (Arabic/English) educational robot that combines a voice conversation pipeline, real-time computer vision, an animated facial display, and motor control into a single cohesive system. Designed to run on a Raspberry Pi 4/5 or a Windows desktop during development, Ropo serves as a platform for classroom interactions, STEM education, and human–robot interaction research.

Core Features

  • Voice Pipeline — Silero VAD + Google ASR + OpenRouter LLM + edge-tts TTS in a real-time streaming architecture
  • Vision Pipeline — Face tracking (OpenCV DNN), gesture recognition (MediaPipe), emotion detection (CNN), object detection (YOLOv8n), obstacle detection, scene segmentation (YOLOv8n-seg)
  • Animated Face — Pygame-based display with five states: IDLE, LISTENING, THINKING, SPEAKING, CURIOUS
  • Motor Control — Serial communication with ESP32/Arduino for physical movement (forward, backward, turn, stop)
  • Session Memory — SQLite-backed conversation history with sliding-window + summarization for context
  • Adaptive Load Shedding — Runtime vision-profile switching (minimal / balanced / full) for thermal management
  • Remote Shutdown — Web API polling client for safe Raspberry Pi shutdown from a mobile app backend
  • Diagnostic Suite — Comprehensive health check covering platform, packages, model files, network, live module tests, and integration

Architecture Summary

Ropo follows a modular pipeline architecture orchestrated by a single entry point (main.py). Each subsystem (voice, vision, LLM, face, hardware) is an independent module communicating via dependency injection and callback-based observation. The voice pipeline runs on two threads (audio capture + segment processing); the vision pipeline runs on its own thread; and the Pygame face runs on the main thread. Modules share context through a shared-context dictionary pattern rather than direct coupling.

4. Detailed File Explanations

4.1 main.py — Entry Point & System Orchestrator

main.py is the single entry point for the entire robot system. Its startup sequence is divided into six clear phases:

  1. Environment & Logging Setup — Loads .env via python-dotenv, detects the platform preset (desktop/RPi4/RPi5), then calls setup_logging() which creates a RotatingFileHandler (5 MB max, 3 backups) to data/robot.log plus a custom AsciiHandler that replaces non-ASCII characters with ? for safe console output. Also sets ultralytics logger to WARNING to reduce noise.
  2. Platform Configuration — On RPi, calls configure_platform() which limits OpenCV and PyTorch to single-threaded mode for thermal efficiency.
  3. Startup Diagnostics — Runs run_startup_diagnostics() checking microphone, speaker, camera, model files, disk space, RAM, and internet connectivity. Results are printed to console.
  4. Module Initialization — Creates instances in dependency order:
    • FaceModule(fullscreen=False) — Pygame face display; started immediately so the face is visible during boot
    • TTSModule(settings.tts) — edge-tts audio playback engine
    • LLMModule() — OpenRouter client + SQLite SessionManager
    • session_id — A conversation session is created with llm.create_session(student_name, language)
    • VisionPipeline() — Camera + all vision modules; opened and started on its own thread
    • MotorController(port) — Serial connection to ESP32; gracefully degrades if unavailable
    • VoicePipeline(...) — Receives all modules via dependency injection, plus a set_face_state callback and vision_context_getter for cross-pipeline data sharing
  5. Main Loop — Calls face.run_main_thread() which enters the Pygame event loop and blocks. All other modules run on their own threads.
  6. Shutdown Sequence — In the finally block: stops the voice pipeline (joins stream + worker threads), stops and closes the vision pipeline, closes the motor serial port, closes the LLM database, and stops the face display.

Cross-platform Port Detection

Motor port is selected at runtime:

if sys.platform == "win32":
    motor_port = "COM3"
else:
    motor_port = "/dev/ttyS0"

Readiness Scoring

After all checks, the system computes a score: passed / total * 100. Thresholds: ≥90 % → READY, ≥70 % → MOSTLY READY, otherwise → NOT READY. The score is printed in green/yellow/red ANSI and saved to the report.

4.3 test_vision_debug.py — Standalone Vision Debug Tool

This tool exercises every vision module in isolation from the main system. It captures 50 frames from the camera and runs each module on every frame, logging per-module timing. Annotated frames are saved every 10 frames to vision_debug_output/.

Debug workflow:

  1. Opens camera via CameraManager
  2. Initializes all modules: FaceIdentityTracker, GestureDetector, EmotionDetector, ObjectRecognitionModule, SceneSegmentationModule, ObstacleDetector
  3. For each frame: runs all modules sequentially, records timing, draws bounding boxes and labels
  4. Logs per-frame summary: faces count, objects count, gesture status, and six timing values
  5. Saves annotated JPGs with overlay info (frame number, face/gesture/emotion/objects, milliseconds)
  6. Prints final summary with detection counts and warnings if no faces or objects were found

4.4 robot_shutdown_client.py — Raspberry Pi Shutdown Poller

A lightweight, resilient polling client designed to run as a systemd service on the Raspberry Pi. It enables remote shutdown from a mobile app or web backend.

Polling architecture:

  • Reads SHUTDOWN_API_URL and SHUTDOWN_TOKEN from environment variables
  • Uses a single requests.Session() with a 10-second timeout
  • Polls GET /shutdown-status every 15 seconds (configurable via SHUTDOWN_POLL_INTERVAL)
  • When the JSON response contains "shutdown": true:
    1. Sends POST /shutdown-reset with the token to acknowledge and reset the flag
    2. Executes sudo shutdown -h now via subprocess
  • Never crashes: all exceptions are caught and logged, and the loop continues indefinitely
  • Individual except clauses for Timeout, ConnectionError, generic RequestException, and any unexpected error

4.6 Deployment Scripts

setup.sh (Linux / Raspberry Pi)

An idempotent 204-line bash script that: checks Python ≥3.10, installs system packages (portaudio, SDL2, OpenBLAS, OpenCV, ffmpeg, libcamera), creates a Python venv and installs requirements, creates project directories with .gitkeep, copies .env.example to .env if missing, downloads OpenCV face detection models from GitHub, applies Pi-specific optimizations (camera interface, gpu_mem=128, picamera2), and runs the health check as a final validation.

setup.ps1 (Windows)

A 167-line PowerShell 5.1+ equivalent. It performs the same steps as setup.sh but uses Test-Path, Copy-Item, Invoke-WebRequest, and PowerShell colour functions. Does not include Pi-specific optimizations.

ropo-shutdown.service

A systemd unit file that runs robot_shutdown_client.py as a service. Configured with Restart=always (5-second delay), EnvironmentFile=/etc/ropo-shutdown.env, and Wants=network-online.target to ensure network availability before starting.

9. Academic Explanation

System Design Philosophy

Ropo was designed from first principles as a modular, event-driven robotic system where each cognitive capability (hearing, seeing, thinking, speaking, moving, expressing) is implemented as an independent module. This follows the Separation of Concerns principle: the voice pipeline does not know how vision works, the face module does not know what the LLM said — they communicate through well-defined interfaces (callbacks, context getters, and dependency injection).

The architecture maps naturally to a sense–think–act robotic control loop:

  • Sense — VAD (hearing) + Camera + Vision modules (seeing)
  • Think — LLM with conversation history and vision context
  • Act — TTS (speaking) + MotorController (moving) + FaceModule (expressing)

Modularity & Dependency Injection

Every module in Ropo is a Python class that could — in principle — be removed, replaced, or tested in isolation. The key enabler is constructor-based dependency injection: VoicePipeline receives all its collaborators as parameters. This means:

  • A MockLLM can replace LLMModule for testing without changing a single line of pipeline code
  • The MotorController gracefully degrades when the ESP32 is not connected — the pipeline simply stops dispatching motor commands
  • Vision context is injected lazily via a getter function, so the voice pipeline does not depend on the vision pipeline's import or lifecycle

Bilingual Support

Arabic/English bilingualism is a first-class architectural concern, not a feature bolted on afterwards:

  • ASR uses language_mode="auto" which lets Google's API detect the language per utterance
  • LLM has separate system prompts for Arabic and English that match the detected language
  • TTS selects the voice model based on the detected language (ar-EG-ShakirNeural for Arabic)
  • Filler phrases are drawn from separate Arabic/English lists with culturally appropriate expressions
  • Session language is set at session creation time and stored in the SQLite database
  • Environment documentation in .env.example is written in both languages

Raspberry Pi Optimizations

The system is designed for resource-constrained deployment on Raspberry Pi hardware:

  • Adaptive load shedding — Vision profiles (minimal/balanced/full) switch module sets at runtime; adaptive frame skipping drops frames when processing exceeds the target interval
  • Platform-specific settings — Camera resolution defaults to 640×480@15 FPS on RPi vs 1280×720@30 FPS on desktop
  • Thermal monitoring — CPU temperature is read from /sys/class/thermal/thermal_zone0/temp; the system can throttle vision processing at 75 °C
  • Single-threaded Torch/OpenCV — configure_platform() calls cv2.setNumThreads(1) and torch.set_num_threads(1) to avoid thread contention on limited CPU cores
  • Graceful degradation — Every component (motor, camera, LLM, microphone) has a runtime-availability check and continues gracefully if unavailable

Graduation Project Value

Ropo demonstrates competency across the full software engineering stack:

  • System Architecture — Multi-threaded pipeline design with clear separation of concerns, dependency injection, and callback-based communication
  • Computer Vision — Integration of four distinct vision techniques (DNN-based face detection, MediaPipe hands, YOLO object detection, CNN emotion classification) into a unified pipeline
  • Natural Language Processing — Bilingual speech recognition, LLM-based conversation with context management, and natural TTS synthesis
  • Embedded Systems — Serial communication with ESP32 for motor control, GPIO-aware systemd service for safe shutdown
  • DevOps & Tooling — Cross-platform setup scripts (bash + PowerShell), automated diagnostics with readiness scoring, logging with rotation, and environment-based configuration
  • Software Quality — Comprehensive error handling (every exception is caught at the appropriate level), graceful degradation, thread-safe queue communication, and watchdog monitoring

The project is fully functional on Windows desktop and deployment-ready for Raspberry Pi 5, making it a complete end-to-end system that bridges academic AI/ML knowledge with practical robotics engineering.
